## What this is

Two repositories that together produce a Microsoft Defender for Endpoint health check report.

| Repo | Visibility | Contents |
|---|---|---|
| `MSalikoc/mde-data-collector` | **public** | `MDE-Collect.ps1`, `New-MdeApp.ps1`, `Test-Parse.ps1`. Runs at the customer. Produces **only** a JSON file |
| `MSalikoc/mde-health-check` | **private** | This repo. Report template, renderer, sample, Word version. Runs at the assessor's own machine |

The split is deliberate: the customer must never see an unreviewed draft report, and the
interpretation layer (best-practice library, narrative drafts, template) stays private.

## Pipeline

```
MDE-Collect.ps1  →  mde-data-<tenant>-<date>.json  →  MDE-Render.ps1  →  <Client>-MDE-Assessment-<date>.html
   (customer)              (plain text, editable)          (assessor)          (edit in browser → Ctrl+P → PDF)
```

Everything the renderer generates is wrapped in `<span class="draft">` and shows a yellow
**(REVIEW)** tag. The consultant clicks each tag (or Alt+click) to approve; there is also an
"Approve all" button. The toolbar counter shows how many remain.

## Where the report content comes from

- `secureConfiguration` (~130 rows of per-control compliance) is the richest source. It fills the
  antivirus, ASR, firewall, network, application and EDR tables, matched **by scid** — never by
  name, see the traps below.
- `asrRules` (from Intune policies) gives the ASR mode column; `asrEvents` gives audit counts.
- Findings are generated by threshold rules in the collector, then the renderer drops any that the
  configuration data contradicts and renumbers them.
- Domain maturity, licence entitlement, top findings, gap analysis, checklist status, compliance
  mapping and the priority matrix are all derived in the renderer.
- 34 of the 110 checklist rows are determined automatically; the rest stay "Not assessed" on
  purpose.

## Traps already paid for — do not rediscover these

1. **PowerShell variable names are case-insensitive.** `$scid = $null` blanked the `$SCID` lookup
   table on the first row and silently disabled a whole mapping pass. Never name a local the same
   as a table, whatever the casing.
2. **`Write-Host` inside a `[regex]::Replace` MatchEvaluator never reaches the console.** Collect
   evidence into a `$script:` list and print it after the replace.
3. **`Set-Chart` must run before the chart-filling pass** near the top of the renderer, otherwise
   the series is computed and thrown away.
4. **`ConvertFrom-Json` objects reject new properties.** Use `Add-Member` (that is what `Set-Chart`
   does) instead of `$d.charts.'New name' = …`.
5. **Assignments inside a function create a local copy.** Use `$script:html` in helper functions;
   top-level `if`/`foreach` blocks are fine.
6. **`[ordered]@{}` rows break `Select-Object -ExpandProperty` and `Measure-Object -Property`.**
   Any table processed by cmdlets inside the collector must be `[pscustomobject][ordered]@{}`.
   This crashed the whole collection the first time a tenant actually had ASR events.
7. **PowerShell treats smart quotes (U+2018/2019/201C/201D) as string delimiters.** A Turkish
   apostrophe inside a single-quoted string shifted every quote pair in the file. `Test-Parse.ps1`
   now warns about this.
8. **`"$var:"` is a parse error** — PowerShell reads the colon as a scope separator. Write
   `"${var}:"`. It fails at parse time, so the whole script refuses to run.
9. **Match configuration controls by scid, not by name.** `'tamper'` matched "prevent tampering"
   (LDAP, 0%) instead of "Turn on Tamper Protection" (100%) and the report claimed tamper
   protection was disabled everywhere.
10. **`@($null)` is a one-element array holding `$null`, not an empty array.** A table the collector
    could not produce — a blocked API, an older JSON — made the renderer die at the first property
    access with "array index evaluated to null". Every table read now goes through the `Rows`
    helper, which filters nulls. Any table can be absent; never assume one is there.
11. **`ConvertFrom-Json` refuses keys that differ only in casing.** `sample-data.json` carried both
    `Exposure Score` and `Exposure score` and could not be loaded at all. The duplicate was never
    needed: PowerShell `-eq` on strings is case-insensitive, so one key fills both KPI boxes.

**2026-08-09 (later)** — `MANUAL-FIELDS.md` was written, because "fill it in by hand" without a
written rule means a different answer every engagement. It defines the two cover KPIs that nothing
computes (`Overall Maturity`, `Control Compliance`), the five maturity levels the template had only
ever named, the severity and effort rubrics, the roadmap bands and the portal-only lookups.

Two things surfaced while writing it. The renderer's `Max(1, Round($score/20))` inherits .NET
banker's rounding, so its real bands are 1: 0–29, 2: 30–50, 3: 51–69, 4: 70–94, 5: 95–100 — a domain
at 90 draws as Integrated and one at 50 drops to Defined. And the security-operations domain divides
resolved alerts by total alerts, which on the test tenant meant one unresolved alert produced a
score of 0. Both are described in `MANUAL-FIELDS.md`; neither is fixed in code yet.

**2026-08-13** — **app-only authentication is proven at a tenant that actually blocks.** A customer
tenant enforcing device-based Conditional Access failed exposure score, configuration score,
recommendations and indicators together with `AADSTS50131`. After `New-MdeApp.ps1 -AppOnly`, all
four collected and only scope notes remained. The open item this handover carried since 2026-08-08
is closed: client credentials are the answer, because an application identity has no device for the
policy to evaluate. Worth knowing for the next engagement: the customer believed they were excluded
from the Conditional Access policy and were still blocked — being excluded from one policy proves
nothing when another scopes the Defender application. Only the Entra sign-in logs, searched by the
correlation ID in the error, say which policy applied.

Three collector fixes came out of it. The error now names the cause and the remedy instead of
printing a raw `AADSTS50131` four times. Optional hunting tables fall back to matching the message
text when the HTTP status cannot be read off the exception — the status was not resolving, so the
licence-dependent firmware table was reporting as a hard failure again despite the earlier fix.
And `Try-Api` now distinguishes a failed call from one that succeeded with no rows, which PowerShell
had been collapsing into the same `$null`: recommendations returning empty usually means Defender
RBAC has not scoped the collecting identity to any device group, and a report that states "no
findings" on that basis is worse than one that reports an error.

The collector README now puts `-AppOnly` in step 2 rather than in a remedy section, and documents
the application permissions honestly — the list had omitted `SecurityConfiguration.Read.All` and
`Ti.ReadWrite.All`. The second is read-write and appears on the customer's consent screen; Defender
publishes no read-only application role for indicators, so a security team meets it for the first
time while approving a tool described as read-only.

**2026-08-13 (later)** — three gaps closed and a questionnaire added.

Host firewall, BitLocker and the misconfiguration table were blank while the controls sat in
`secureConfiguration`. The misconfiguration table had required a control to apply to 50 devices; on a
nine-device tenant nothing qualified and it rendered empty. The floor is now relative to the estate.
Rows are only filled where a control genuinely covers them - Credential Guard is still blank rather
than filled from "disable local storage of passwords", which would have been trap 9 in a new costume.

Secure score impact was reading the current score, which in that list is near zero by definition; the
number wanted is the ceiling, which lives on the control profiles endpoint.

A 677-rule custom detection inventory cannot be shown five arbitrary rows at a time. The rows now
lead with disabled rules and then severity, and the narrative carries the real scale.

`New-Survey.ps1` and `survey-questions.psd1` produce a customer questionnaire for the fields no API
exposes. Questions are written by hand - asking "Data storage region" as though it were a question
tells the customer nothing - with a full sentence, a note explaining what is meant, and a closed
answer set. The generator validates every question against the template and reports both questions
whose target row has gone and blanks that have no question yet, so the two cannot drift apart. The
renderer takes `-SurveyFile`; collected data always wins, and answers arrive labelled
**Self-reported**, because a customer assertion and a measurement are not the same claim.

Two traps paid for while building it: an apostrophe inside a single-quoted string in a `.psd1` closes
the string (the cousin of trap 7), and a regex evaluator that returns the captured group rather than
the whole match silently deletes the `<tr>` tags around every row it touches.
